# Безопасность

Единственная по-настоящему опасная ошибка здесь — дюп. Ниже то, что закрыто в первой версии, и то, что осознанно
оставлено на потом.

## Правила, на которых всё держится

1. **Предмет живёт в одном месте.** Инвентарь, эскроу или очередь выдачи. Журнал `item_movements` позволяет это
   проверить, а не просто заявить: тесты после каждого сценария сверяют, что каждое перемещение начинается там, где
   закончилось предыдущее.
2. **Переход состояния — охраняемый UPDATE.** Ничего не происходит, если строка уже не в том состоянии, которое
   ожидалось. Повтор любой операции безвреден по построению, а не по дисциплине.
3. **Сначала база, потом инвентарь, и явный `saveData()` между ними.** См. ARCHITECTURE.md; без этого барьера падение
   сервера дублировало бы предметы при каждом выкладывании лота.
4. **Выдача только через очередь.** Прямой выдачи нет даже когда игрок стоит рядом, поэтому у восстановления одна
   точка входа.
5. **Сомневаешься — не трогай.** Несовпадение версии данных сервера, сделка без ожидаемого эскроу, нечитаемый предмет:
   плагин останавливается и пишет событие, а не угадывает.

## Проверенные сценарии

| Сценарий | Что происходит | Тест |
|---|---|---|
| Отмена уже отменённого лота | ничего, предметы выдаются один раз | `cancelIsIdempotent` |
| Двойное завершение сделки | вторая попытка ничего не выдаёт | `completingTwiceChangesNothing` |
| Двойное подтверждение | учитывается один раз (`PRIMARY KEY (trade_id, party)`) | `completeTrade` |
| Два покупателя на один лот одновременно | выигрывает один, второй получает отказ и сохраняет предметы | `concurrentOffers` |
| Чужой лот, чужая сделка | отказ, ни одного перемещения | `onlyTheOwnerMayCancel`, `outsidersCannotConfirm` |
| Подарок не тому игроку | отказ по UUID **и** по нику | `giftChecksTheRecipient` |
| Полный инвентарь | предметы остаются в очереди | `fullInventoryKeepsItemsWaiting` |
| Игрок не готов (мёртв, в GUI, не вошёл в AuthMe) | выдача откладывается | `waitsUntilThePlayerIsReady` |
| Падение до изъятия предметов | предметы остались у игрока, лот не создан | `crashBeforeRemoval` |
| Падение после изъятия | предметы вернулись через очередь | `crashAfterRemoval` |
| Падение во время выдачи | посылка снова в очереди | `crashWhileHandingOver` |
| Падение после выдачи | посылка закрыта, второй раз не выдаётся | `crashAfterItemsArrived` |
| Повторный запуск восстановления | ничего не меняется | `recoveryIsIdempotent` |
| Эскроу под завершённым лотом | возвращается при старте | `orphanedEscrowIsReturned` |
| Откат сервера на старую версию | операция помечается `MANUAL`, ничего не выдаётся | `differentDataVersionIsNotGuessed` |
| Прерванное предложение обмена | лот снова активен, предметы у покупателя | `interruptedOfferReleasesTheListing` |
| Сделка без ожидаемого эскроу | не завершается | `completionChecksTheEscrow` |
| Несуществующий лот или сделка | понятная ошибка, ноль изменений | `unknownListing` |

Одна настоящая дыра была найдена именно тестами уже в процессе: восстановление при старте возвращало в очередь
выдачи, которые на самом деле дошли до игрока. Игрок получал вещь дважды. Исправлено тем, что старт такие записи не
трогает — решение принимается при входе игрока по отпечатку инвентаря (`crashAfterItemsArrived`).

## Окна

Главное решение: **в окне рынка никогда не лежат предметы**. Создание лота — это отметка галочками собственных вещей
игрока; они остаются в его инвентаре до самого конца, а рынок забирает ровно отмеченное одной транзакцией. Предмет
физически не может «жить» только в открытом окне, и поэтому не может оттуда исчезнуть, удвоиться или пережить
перезагрузку плагина.

Что из этого следует:

| Приём | Почему не работает |
|---|---|
| Shift-клик из своего инвентаря в окно | все клики отменяются, что бы ни было под курсором |
| Перетаскивание (drag) через слоты окна | отменяется, если задет хоть один слот окна |
| Цифровые клавиши 1–9 и F (`NUMBER_KEY`, `SWAP_OFFHAND`) | отменяются: они меняют слот инвентаря, пока курсор над окном |
| Двойной клик (сбор одинаковых предметов со всего экрана) | отменяется |
| Клик мимо окна, выбрасывание `Q` | отменяется, курсор в наших окнах всегда пуст |
| Креативный клик | отменяется |
| Новый тип клика в будущей версии | считается неизвестным и отменяется |
| Воронка или другой плагин тянет предметы из окна | `InventoryMoveItemEvent` отменяется |
| Выключение плагина с открытым окном | все окна закрываются в `onDisable` |
| Картинка из окна оказалась в инвентаре | помечена в persistent data, вычищается при входе, запись в лог |

Правило проверено не примерами, а таблицей: `GuiPolicyTest` прогоняет **каждый** тип клика Bukkit по слотам окна,
слотам инвентаря игрока и «мимо окна». Ни один не остаётся неотменённым.

Отдельно: окно никогда не открывается изнутри обработчика клика — только следующим тиком. Открытие окна внутри события
дублирует предмет на курсоре, и это самая частая ошибка в чужих плагинах. И пока окно открыто, рынок не кладёт в
инвентарь ничего: выдача идёт после закрытия.

## Что нашёл аудит после готовности

| Находка | Что сделано |
|---|---|
| Восстановление при старте возвращало в очередь выдачи, которые уже дошли до игрока — дюп | старт такие записи не трогает, решает вход игрока по отпечатку |
| Двойной клик по «Выложить» оставлял пустой черновик | второй клик игнорируется, пока первый не закончил |
| `/market deliveries` при открытом окне молча ничего не делал | окно закрывается, потом выдача |
| Забытые лоты висели вечно, вещи заперты | необязательное истечение, возврат владельцу, защищено теми же охраняемыми UPDATE |
| Смена ника на offline-сервере запирала эскроу за старым UUID | `/market admin reassign`, одна транзакция, запись в журнал |

## API

- слушает только `127.0.0.1`;
- токен минимум 24 символа, сравнение постоянное по времени, в лог не попадает;
- ограничение частоты на адрес;
- у всех действий обязательный `Idempotency-Key`, ответ сохраняется и повторяется;
- сайт передаёт только UUID игрока — право на действие проверяет ядро, а не сайт;
- предметы через API не двигаются вообще: даже отмена лота лишь ставит их в очередь выдачи, забрать может только сам
  игрок в игре;
- ключ, использованный на другой путь, — ошибка (иначе ответ от одной операции подставился бы другой).

## Что ещё не закрыто

- **Смена ника на offline-сервере** создаёт нового игрока. Перенос есть (`/market admin reassign`), но он ручной и
  намеренно: на offline-сервере «тот же ник» не значит «тот же человек», и автоматика здесь опаснее неудобства.
- **Настоящий NBT в тестах.** MockBukkit подделывает сериализацию, поэтому round-trip настоящего зачарованного
  предмета проверяется вручную на сервере (пункт 11 в DEPLOYMENT.md), а не в CI.
- **Один экземпляр на базу.** Если запустить два сервера на одном файле `market.db`, SQLite защитит запись, но
  логика — нет. Не делайте так.
- **Откат мира без базы** (и наоборот) — массовый дюп. Восстанавливать только вместе.

## Чего в плагине нет намеренно

Выполнения команд снаружи, RCON, прямого SQL из Minecraft-части в чужие базы, записи файлов по пути из запроса,
выбрасывания предметов на землю как способа доставки.
