# Восстановление после сбоя

Плагин исходит из того, что сервер может исчезнуть в любой момент: `kill -9`, OOM, пропажа питания. Поэтому `onDisable`
считается вежливостью, а не механизмом: все гарантии должны выполняться и без него.

## Что происходит при старте

1. Читается отметка о чистой остановке. Если её нет, в лог идёт предупреждение — дальше проверка одна и та же, просто
   становится понятно, чего ждать.
2. **Эскроу-сироты.** Строки в состоянии `HELD`, чей лот или сделка уже завершены (или у которых вообще нет родителя),
   превращаются в посылки владельцу. Это единственное, что можно решить без инвентарей.
3. **Прерванные выдачи** (`CLAIMING` с чужим boot id) только считаются и пишутся в лог. Их **не** возвращают в очередь:
   понять, дошли ли предметы, можно лишь заглянув в инвентарь игрока.

В логе:

```
[OurServerMarket] The last run of the server did not stop cleanly; checking the marketplace.
[OurServerMarket] Recovery: 2 stack(s) returned to their owners, 1 handover(s) waiting for their player to log in.
```

## Что происходит при входе игрока

С AuthMe — после успешного входа (AuthMe до этого прячет инвентарь, и любой отпечаток был бы мусором). Без AuthMe —
через секунду после захода.

Для каждого незакрытого намерения этого игрока сравнивается отпечаток инвентаря:

| Операция | Отпечаток совпал | Отпечаток изменился |
|---|---|---|
| Взятие предметов (`LIST_OFFER`, `TRADE_OFFER`) | изъятие не пережило падение → `ABORTED`, всё осталось у игрока | изъятие прошло → предметы возвращаются посылкой |
| Выдача (`CLAIM`) | предметы не дошли → посылка снова `PENDING` | предметы дошли → посылка `CLAIMED` |

Если версия данных сервера отличается от записанной в намерении (откат Minecraft на старую версию), решение не
принимается: намерение помечается `MANUAL`, в журнал пишется `RECOVERY_MANUAL`. Разбирает администратор.

## Почему отпечаток работает

Он снимается **в том же тике**, в котором предметы изымаются, и сразу после этого файл игрока сбрасывается на диск
(`Player#saveData()`). Между снятием отпечатка и сохранением инвентарь никто изменить не может, поэтому «совпал» и «не
совпал» действительно означают то, что нужно.

Остаточный риск: переименование файла игрока не форсирует fsync, поэтому потеря питания (не падение процесса) может
откатить последние секунды. Это единственный случай, где расхождение возможно, и именно он виден администратору как
незакрытое намерение.

## Привязанный сундук

У сундука нет барьера долговечности. Файл игрока сбрасывается на диск командой, один чанк — нельзя, а `World#save()`
на каждое выставление лота — это сотни миллисекунд на главном потоке по запросу из браузера.

Поэтому мир не заставляют быть долговечным. Вместо этого каждая операция получает **номер**, и этот номер пишется в
persistent data самого блока (обеих половин большого сундука). Свойство, на котором всё держится, стандартное, и оно
проверено на сервере руками: PDC блока переживает перезапуск и **теряется вместе с несохранённым чанком**. Содержимое
и номер живут в одном блоке, поэтому разойтись не могут: чанк записался — записались оба, не записался — откатились
оба.

`S` — номер, прочитанный из блока после перезапуска, `D` — отпечаток сундука.

| Где упали | База | Сундук на диске | Итог |
|---|---|---|---|
| до первой транзакции | пусто | не тронут | вещи только в сундуке |
| после неё, до изъятия | `INTENT` | `D=до`, `S=N-1` | `ABORTED`, вещи только в сундуке |
| изъял, чанк **не** сохранён | `INTENT` | `D=до`, `S=N-1` | `ABORTED`, вещи только в сундуке |
| изъял, чанк **сохранён** | `INTENT` | `D=после`, `S=N` | в сундуке их нет, лота нет → посылка владельцу |
| лот создан, чанк **не** сохранён | `FINALIZED`, `applied_seq=N` | `D=до`, `S=N-1` | план повторяется, в эскроу ровно одна копия |
| лот создан, чанк сохранён | `FINALIZED`, `applied_seq=N` | `D=после`, `S=N` | согласны, ничего не делаем |
| `D` ни то, ни другое; `S > applied_seq`; половины спорят | любое | любое | `MANUAL`, сундук заморожен, **ничего не двигается** |

Третью и пятую строки различает не мир, а состояние намерения в базе — оно долговечно: `INTENT` значит «второй
транзакции не было» → отмена; `FINALIZED` значит «эскроу уже есть» → повторить изъятие.

Последняя строка и делает схему безопасной, а не хитрой: **алгоритм никогда не угадывает.** `S > applied_seq` — это
откат базы из резервной копии, тоже `MANUAL`.

### Когда сверка запускается

При старте — сразу для сундуков с незакрытой операцией, ради них не жалко подгрузить чанк. Дальше: при загрузке чанка,
при первом же обращении к сундуку и раз в минуту для отставших. Промежуток между появлением чанка и сверкой закрывает
заморозка: **пока сверка не прошла, сундук не открывается никому, включая владельца**, и рынок из него ничего не
отдаёт.

Сундук, оставленный администратору (`MANUAL`), остаётся замороженным. Владелец может привязать другой сундук — старая
привязка снимается, а незакрытое намерение остаётся в базе для разбора.

### Если блок исчез

WorldEdit, `/setblock`, порча чанка — эти события не отменяемы. Сундук помечается `BROKEN`, в журнал идёт
`CHEST_LOST`, сайт получает `CHEST_MISSING`. Рынок при этом ничего не теряет: всё, что принадлежит ему, лежит в
`escrow_items` и `pending_deliveries`, а в сундуке — только ещё не выставленное. Здесь и окупается решение «сундук —
только источник».

## Ручной разбор

```sql
-- незакрытые намерения
SELECT tx_id, op, player_uuid, state, created_at FROM intents
 WHERE state IN ('INTENT','APPLIED','MANUAL') ORDER BY created_at;

-- зависшие выдачи
SELECT id, player_uuid, attempts, claim_boot_id FROM pending_deliveries WHERE state = 'CLAIMING';

-- что вообще происходило с конкретной вещью
SELECT ts, from_holder, to_holder, amount, tx_id FROM item_movements WHERE item_uid = '…' ORDER BY id;

-- события вокруг лота
SELECT ts, type, actor_uuid, detail FROM events WHERE listing_id = 12 ORDER BY id;

-- склады и их номера операций
SELECT id, owner_uuid, state, next_seq, applied_seq, verified_boot_id FROM bound_chests WHERE state = 'BOUND';

-- незакрытые операции по сундуку, вместе с планом
SELECT c.tx_id, c.chest_id, c.seq, c.plan, i.state FROM chest_intents c JOIN intents i ON i.tx_id = c.tx_id
 WHERE i.state IN ('INTENT','MANUAL');
```

Посылка, зависшая в `CLAIMING`, разрешается сама, когда игрок зайдёт. Если игрок не заходит месяцами, строку можно
вернуть в очередь вручную — но только убедившись по `item_movements`, что предметы действительно не у него:

```sql
UPDATE pending_deliveries SET state = 'PENDING', claim_tx = NULL, claim_boot_id = NULL WHERE id = ?;
```

## Чего восстановление не делает

- не удаляет строки `items`: нечитаемый или непонятный предмет остаётся в базе с пометкой, чтобы его можно было
  разобрать вручную;
- не угадывает при смене версии Minecraft;
- не возвращает предметы «на всякий случай»: лишний возврат — это тот же дюп, только с другой стороны.
