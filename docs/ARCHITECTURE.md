# Архитектура

## Слои

```
bukkit/   команды, слушатели, инвентарь игрока, блоки сундуков, кодек предметов
   ↓
core/     MarketService: правила, переходы состояний, оба протокола перемещения
   ↓
storage/  Database + репозитории: SQLite, миграции, журнал
   ↑
http/     ApiServer: локальный API v1 для сайта
```

Зависимости идут только вниз. `core` **не импортирует ни одного класса Bukkit** — предмет для него это `ItemBlob`
(байты + количество + короткое описание). Благодаря этому 90 % логики проверяется тестами без запуска сервера, а
именно эту логику и нельзя ошибиться.

Единственный класс, который двигает предметы, — `MarketService`. Не «сервис слоя», а буквально одно место в коде, где
предмет меняет владельца. Всё остальное к нему обращается.

## Два протокола

### Забрать предметы у игрока

```
1. снять отпечаток инвентаря (sha256 по NBT содержимого, брони и левой руки)
2. транзакция: записать строки items + intent(INTENT, отпечаток)   ← коммит
3. изъять предметы из инвентаря
4. player.saveData()                                                ← барьер долговечности
5. транзакция: intent → APPLIED, строки escrow, движения в журнале, intent → FINALIZED
```

Зачем шаг 4. База коммитит мгновенно, а файл игрока сбрасывается на диск автосейвом раз в несколько минут. Без явного
`saveData()` падение сервера между шагом 5 и автосейвом означало бы: в базе предмет в эскроу, в восстановленном
`playerdata` он же в инвентаре. Это дюп, и он случался бы при каждом падении, а не в экзотике.

Что делает восстановление при входе игрока:

| Где упали | Отпечаток при входе | Решение |
|---|---|---|
| до шага 3 | совпал | интент ABORTED, предметы у игрока, лот не создан |
| между 3 и 5 | не совпал | предметы возвращаются через очередь выдачи |
| версия данных сервера изменилась | — | интент MANUAL, ничего не трогаем, событие в журнал |

### Отдать предметы игроку

```
1. снять отпечаток инвентаря
2. транзакция: доставка PENDING → CLAIMING + intent(INTENT)          ← коммит
3. inventory.addItem (всё или ничего, заранее проверено на копии)
4. player.saveData()
5. транзакция: доставка CLAIMING → CLAIMED, движение в журнале, intent → FINALIZED
```

Прямой выдачи «в обход очереди» нет вообще: даже когда игрок стоит рядом и место в инвентаре есть, предмет сначала
становится строкой в `pending_deliveries`. Одна дорога — одна точка восстановления.

При падении между 3 и 5 запись остаётся в CLAIMING. **Восстановление при старте её не трогает** — понять, дошли ли
предметы, можно только заглянув в инвентарь, а это возможно лишь при входе игрока. Раньше здесь была ошибка: старт
возвращал такие записи в очередь, и игрок получал вещь второй раз. Тест `crashAfterItemsArrived` её и поймал.

### Забрать предметы из привязанного сундука

Третий протокол, и он существует только потому, что у сундука нет четвёртого шага: сбросить на диск один чанк нельзя.

```
  найти сундук, отказать, если по нему есть незакрытое намерение
  before = прочитать сундук                                     ← переход на главный поток
  сверить отпечаток всего сундука и каждый (слот, sha256, количество)
  N = next_seq

  транзакция 1 ── строки items
               ── intent(source=CHEST, INTENT, отпечаток «до»)
               ── chest_intents(номер N, отпечаток «до», отпечаток «после», план)   ← коммит

  переход на главный поток ── перепроверить план по живому сундуку
                           ── изъять ровно план, всё или ничего
                           ── записать номер N в PDC обеих половин                  ← всё в одном тике

  транзакция 2 ── intent → APPLIED, лот, listing_items, эскроу
               ── движение CHEST:<id> → LISTING:<id> в журнале
               ── applied_seq = N, intent → FINALIZED                               ← коммит
```

Сохранения мира нет нигде: чанк пишется тогда, когда Paper сочтёт нужным. Номер операции и содержимое лежат в одном
блоке, поэтому мир не может сохранить одно без другого, а сверка после перезапуска по двум числам понимает, чья
сторона отстала. Таблица всех случаев — в [RECOVERY.md](RECOVERY.md).

Вторая половина «всё в одном тике» — то, что изъятие и запись номера делаются внутри одной задачи главного потока.
Мир пишется между тиками, так что промежутка, в который может влезть сохранение, просто нет.

## Переходы состояний

Каждый переход — охраняемый UPDATE:

```sql
UPDATE listings SET state = 'PENDING_TRADE' WHERE id = ? AND state = 'ACTIVE'
```

Дальше операция идёт только если изменилась ровно одна строка. Из этого бесплатно получаются:

- **идемпотентность** — повтор не сработает, второй вызов просто ничего не меняет;
- **гонки** — двое покупателей на один лот: выигрывает тот, чей UPDATE прошёл;
- **порядок** — сделка не может «завершиться» из состояния, из которого это не разрешено.

Завершение сделки идёт одной командой, которая внутри себя проверяет и подтверждения, и количество эскроу:

```sql
UPDATE trades SET state = 'COMPLETED' WHERE id = ? AND state = 'CONFIRMED'
  AND (SELECT COUNT(*) FROM trade_confirmations WHERE trade_id = ?) = 2
  AND (SELECT COUNT(*) FROM escrow_items WHERE trade_id = ? AND state = 'HELD') = expected_escrow_count
```

Ни одно подтверждение не может проскочить между проверкой и обновлением, потому что это одна операция.

## Потоки

- всё, что трогает инвентарь **или блок**, — только главный поток сервера;
- запись в SQLite для операций с предметами — синхронно, в том же тике (локальная запись в WAL занимает доли
  миллисекунды, а асинхронность тут означала бы потерянные предметы);
- HTTP-обработчики живут в своём пуле и ходят только в базу — кроме запросов про сундук, которые переходят на главный
  поток через `MainThread` и ждут ответа;
- соединение с базой одно и синхронизировано: две транзакции не могут пересечься, а вложенная транзакция — ошибка, а не
  тихий no-op.

Отсюда одно правило, которое нельзя проверить компилятором: **задача, отданная на главный поток, не трогает базу.**
Иначе главный поток ждал бы монитор соединения, который держит HTTP-поток, ждущий главный поток, — взаимная блокировка
без выхода. `BukkitContainerPort` поэтому собран вообще без поля `Database`: правило держится структурой, а не
памятью. По той же причине `createListingFromChest` написан плоской последовательностью «транзакция → переход →
транзакция», а не переходом внутри лямбды транзакции.

Ожидание тоже устроено осторожно. Задачу, которая **ещё не началась**, по таймауту в две секунды можно бросить:
браузер получит `CHEST_UNAVAILABLE`, и ничего не произошло. Задачу, которая **уже двигает вещи в сундуке**, бросать
нельзя ни при каких обстоятельствах — наполовину изъятый сундук и ошибка в браузере это единственный исход, которого
схема не переживёт. Различает их compare-and-set по состоянию задачи: бросить можно только `PENDING`, и сама задача
отказывается стартовать, если её уже бросили.

## Личность игрока

Ключ везде — Minecraft UUID. Ник хранится рядом и обновляется при входе, но ничего не решает.

Сервер работает в offline-режиме, поэтому UUID вычисляется из ника: смена ника = другой игрок с точки зрения
Minecraft. Схема к этому готова (`identities.account_id` позволяет связать несколько UUID в один аккаунт), но
автоматического связывания нет намеренно: на offline-сервере «тот же ник» не значит «тот же человек». Перенос — ручная
административная операция, она появится во втором этапе.

## Чего в коде нет

- прямого доступа сайта к базе, к инвентарям и к `playerdata`;
- выполнения команд, пришедших снаружи;
- выбрасывания предметов на землю как способа доставки;
- хранения предметов в памяти между тиками — всё, что не в базе, не существует.
